# 연구 번들 리페어/두뇌 import 설명서

이 문서는 GPT Pro 웹 세션에서 만든 `*_nslab_episode_bundle.md` 연구 결과를
프로젝트 두뇌 원료로 넣을 때의 운영 절차를 정리한다.

수백 개 이상의 신규 연구도 월별·병렬로 먼저 처리하지 않는다. 원본 하나를 선택해
repair와 검수를 끝낸 뒤에만 다음 원본으로 넘어간다. 새 출력 구조를 발견하면 해당
날짜만 처리하는 예외를 넣지 않고, 같은 구조 계열을 읽는 범용 adapter/alias 규칙과
회귀 테스트로 확장한다. 확장한 규칙으로 현재 파일과 기존 fixture를 다시 통과시킨다.

이 문서의 검수는 repair 결과의 구조·손실·import 가능성 검사다. 연구 내용을 다시
판단하는 별도 semantic reviewer를 실행하지 않고, 후공정에서 BLIND 연구를 다시
판정하지 않는다. BLIND 계약은 `docs/research_prompt.md`를 수행한 연구 번들의 선언을
보존한다.

## 재실행 방지 계약

순차 처리의 단위는 **원본 파일 하나**다. 현재 파일을 닫을 때까지 다음 파일을
시작하지 않으며, 이미 `sequential_repair_manifest.v2.jsonl`에 결과가 있는 이전
파일은 다음 실행에서 다시 repair·inspect·import하지 않는다. 같은 파일 안에서
deterministic 출력을 확인하기 위해 repair를 두 번 호출하는 것은 과거 파일을
재처리하는 것이 아니다.

다음 파일로 넘어가는 정상 흐름은 아래와 같다.

```text
현재 원본 1개 선택
→ 그 원본만 repair/검수
→ READY_FOR_IMPORT이면 결과 봉인
→ PRESERVED_PARTIAL/DEFERRED이면 사유와 원본을 보존
→ 다음 원본 1개 선택
```

parser/repair의 범용 규칙을 실제로 바꾼 경우에도 전체 과거 자료나 월 전체를
자동으로 다시 돌리지 않는다. 회귀 테스트 후 영향이 확인된 source SHA/date만
`--retry-existing --source-date` 또는 `--source-path`로 명시해 재검수한다. 월간
서브에이전트 검토는 최신 결과를 읽기만 하며 repair, import, 재실행을 하지 않는다.
따라서 같은 파일의 manifest 행이 무한히 쌓이지 않고, 재검수도 명시한 파일에만
한정된다.

각 월의 마지막 파일을 닫은 뒤에는 별도 서브에이전트에게 그 월의 manifest와 repaired
파일을 읽기 전용으로 점검시킨다. 이것은 semantic 판정을 새로 만드는 reviewer가
아니며, 파일·코드·원본 연구를 수정하거나 production import를 실행하지 않는다. 아래
brain ingest 조건만 독립적으로 대조한다.

```text
record/ID/type/payload 보존, isolated import/deep audit 손실 0,
provenance closure, training_eligible/sample_weight, semantic 제외 보존,
최신 SHA와 ready_for_import 결속, production 저장소 불변
```

월간 점검에서 공통 parser/repair 결함이 보이면 범용 규칙과 회귀 테스트를 추가하고
영향받은 파일만 다시 repair한다. 날짜·종목별 예외나 연구 재실행은 만들지 않는다.

source와 repaired의 population 관계가 동일하고 record/lineage/provenance/import가
닫혔지만 현재 계약의 case-artifact만 없는 legacy 번들은
`LEGACY_CONTRACT_POPULATION_QUARANTINED` 경고로 보존할 수 있다. 이것은 current
gold 승인이 아니며, 실제 closure mismatch·provenance 미해결·UTF-8 손상·record
손실은 계속 partial로 남긴다.

## 기본 운영 계약

```text
1. 원본 한 파일의 경로·SHA-256·크기를 봉인한다.
2. 원본은 수정하지 않고 별도 경로에 repair한다.
3. 원본→repair의 artifact, record, provenance, population을 대조한다.
4. 손실이나 잘못된 제외가 parser/repair 문제면 범용 규칙과 회귀 테스트를 추가한다.
5. 같은 파일을 다시 repair하고 검수한다.
6. 연구 번들에 명시된 semantic 모순과 연결된 positive record만 학습에서 제외한다.
7. 현재 파일이 닫힌 뒤에만 날짜순 다음 파일로 넘어간다.
```

범용 확장은 wrapper, heading, fence, 필드 alias, 중첩 위치, ID 관계처럼 구조로
정의한다. 파일명, 날짜, 종목, 테마를 조건으로 삼는 맞춤형 패치는 금지한다.

## 목표와 종료점

이 단계의 목표는 원본 연구를 실제 두뇌에 즉시 import하는 것이 아니다. 원본에 있는
연구내용을 최대한 보존·정규화하고, 실제 importer와 동일한 격리 검증까지 통과한
`READY_FOR_IMPORT` repaired bundle을 만드는 것이다.

```text
원본 연구 MD
→ 원본 census
→ 표준 brain record repair
→ 원본 대비 무손실·모집단·provenance 검수
→ 명시적 semantic 모순 record만 training_eligible=false
→ 임시 저장소 import/deep audit
→ READY_FOR_IMPORT repaired MD + quality gate
```

한 파일이 `READY_FOR_IMPORT`로 닫히기 전에는 다음 파일을 시작하지 않는다. 원본에 실제
machine payload가 없다면 내용을 만들지 않고 `PRESERVED_SOURCE_PAYLOAD_ABSENT`로 원본과
상태만 보존한다. Phase A에서는 production research/memory/brain 저장소를 수정하지 않으며
연구를 다시 수행하지 않는다.

## 폴더 원칙

실전 누적용 폴더는 `research/` 아래를 쓴다.

```text
research/inbox/bundles/raw/
research/inbox/bundles/repaired/
```

`docs/pilot_bundles/`와 `docs/pilot_repairs/`는 파일럿 성공 예시 보관용이다.
새 연구를 계속 모을 때는 pilot 폴더가 아니라 `research/inbox/bundles/raw/`에 넣는다.

## 한 줄 요청

순차 repair와 검수를 이미 통과한 repaired 파일만 import할 때 Codex에게 이렇게 요청하면 된다.

```text
research/inbox/bundles/repaired에서 검수 완료로 표시된 번들만 두뇌에 import해줘.
warehouse/brain audit까지 확인하고, 미검수 파일은 건드리지 마.
```

누적 연구의 순차 repair를 맡길 때는 다음처럼 요청한다.

```text
docs/설명서.md의 기본 운영 계약대로 날짜순 한 파일씩 진행해줘.
각 파일을 repair·검수하고, parser/repair 문제면 날짜별 예외 없이 범용 규칙과
회귀 테스트를 보강해 같은 파일을 재검증한 뒤 다음 파일로 넘어가.
원본은 수정하지 말고, 실제 연구 근거가 없는 내용은 창작하지 마.
```

다음 원본 한 파일을 맡길 때는 이렇게 말하면 된다.

```text
이 파일 하나를 docs/설명서.md의 기본 운영 계약대로 repair하고 검수해줘.
범용 parser/repair 보강이 필요하면 같은 파일을 재검증해 닫고, 다음 파일은 시작하지 마:
research/inbox/bundles/raw/YYYYMMDD_nslab_episode_bundle.md
```

## 파일을 어디에 두나

웹 세션에서 받은 원본 연구 MD는 먼저 여기에 둔다.

```text
research/inbox/bundles/raw/
```

repair 결과는 여기에 생성한다.

```text
research/inbox/bundles/repaired/
```

원본은 웹 세션에서 받은 연구 결과 그대로 보존하고, 두뇌 import는 repaired 파일로 한다.

## Phase A: 한 파일을 import 직전으로 만들기

일반 실행은 기존 manifest 결과를 엔진 해시가 바뀌었다는 이유만으로 다시 돌리지
않는다. 현재 파일 하나만 `--max-files 1`로 처리하고, 기존 파일을 다시 볼 때만
`--retry-existing --source-date YYYYMMDD` 또는 정확한 `--source-path`를 명시한다.
그 파일이 닫힌 뒤에만 다음 날짜로 이동한다. 여러 파일을 한 번에 계속 처리하는
`--continue-after-blocker`는 사용하지 않는다.

```text
1. 원본 경로·SHA-256·크기·내부 거래일 봉인
2. 모든 machine artifact와 brain_delta 원본 census
3. 별도 .work/<source_sha>/candidate.repaired.md 생성
4. record/type/payload/provenance/eligibility/available_from 정규화
5. 원본→repaired artifact·record lineage와 모집단 대조
6. 명시적으로 모순된 positive semantic 관계와 연결된 record만 학습 제외
7. inspect-bundle 검증
8. 격리된 임시 저장소에 import-bundle --validate --accept
9. 임시 저장소 deep audit 후 완전 삭제
10. 실패가 parser/repair 문제면 범용 규칙+회귀 테스트 보강
11. 같은 원본을 다시 repair·검수
12. 통과본과 SHA 결속 quality gate를 repaired/<연도>/에 확정
13. `.work/<source_sha>/`의 census·lineage·isolated import/deep-audit sidecar는
    월간 read-only 감사와 재현 검증을 위해 보존한다. `candidate-a/b.repaired.md`처럼
    재검증에 필요 없는 중간 후보 파일만 sidecar의 SHA와 manifest가 확정된 뒤 선택적으로
    정리하고, 다음 파일로 이동한다.
14. 월의 마지막 파일을 닫으면 읽기 전용 brain ingest 월간 검토를 실행
```

회고용 case artifact가 brain_delta에 빠져 있어도 무조건 내용을 창작해 채우지 않는다.
`retrospective_only=true`, `blind_candidate_generated=false`, `training_eligible=false`와
명시적 no-bridge 사유가 모두 있는 경우에 한해 case의 기존 ID/fact/source만 복사한
zero-weight audit/context record를 deterministic하게 추가할 수 있다. 이 record는
provenance closure와 derivation hash를 갖지만 positive training 사례가 아니다.

정규화 대상은 최소한 다음을 포함한다.

```text
brain_delta와 record type/payload
source/fact/inference ledger와 provenance closure
candidate screening/ranking/final watchlist
outcome/postmortem/negative/newsless/beneficiary case
semantic witness의 기존 판정과 record 연결
training_target/training_eligible/sample_weight/available_from
front matter/manifest/count/hash/direct ingest contract
```

repair는 semantic 판정을 새로 만들지 않는다. 기존 artifact의 명시적 positive 판정이
자기 필드와 모순되면 연결된 positive training record만 아래처럼 내린다.

```text
training_eligible = false
sample_weight = 0.0
training_exclusion_reason = semantic_contract_failed
```

negative control, audit, context, counterexample record는 같은 relation ID를 포함해도 제외하지
않는다. 제외 record도 삭제하지 않고 원형과 provenance를 보존한다.

## Phase B: 검수 완료본 실제 import

모든 원본의 Phase A가 끝난 뒤 `READY_FOR_IMPORT`와 quality gate가 일치하는 repaired
bundle만 실제 프로젝트 저장소에 import한다.

```text
READY_FOR_IMPORT repaired bundles
→ import-bundle --validate --accept
→ warehouse rebuild/verify
→ production provider를 사용한 brain rebuild --mode llm-full
→ memory index/brain/coverage/lookahead/provenance audit
```

## 실제 명령

단일 파일 임시 repair:

```bash
python -m news_scalping_lab.tools.repair_research_bundle research/inbox/bundles/raw/YYYYMMDD_nslab_episode_bundle.md -o research/inbox/bundles/.work/SOURCE_SHA/candidate.repaired.md
```

임시 repaired 파일 검사:

```bash
python -m news_scalping_lab.cli research inspect-bundle research/inbox/bundles/.work/SOURCE_SHA/candidate.repaired.md
```

Phase A의 격리 import는 실제 프로젝트 루트가 아닌 임시 저장소에서 수행하고 삭제한다.
Phase B에서 quality gate까지 통과한 최종 repaired 파일만 실제 import/accept한다.

```bash
python -m news_scalping_lab.cli research import-bundle research/inbox/bundles/repaired/YYYYMMDD_nslab_episode_bundle.repaired.md --validate --accept
```

warehouse 갱신:

```bash
python -m news_scalping_lab.cli warehouse rebuild
python -m news_scalping_lab.cli warehouse verify
```

production brain 갱신:

```bash
python -m news_scalping_lab.cli brain rebuild --mode llm-full
python -m news_scalping_lab.cli memory rebuild-index --production
python -m news_scalping_lab.cli brain audit --deep
python -m news_scalping_lab.cli doctor --production
```

전체 코드 검증:

```bash

```

## READY_FOR_IMPORT 통과 기준

각 repaired bundle은 최소한 아래가 외부 계산값으로 통과해야 한다. 번들 내부의
`ACCEPT_FULL`이나 `passed=true` 자기선언만으로 통과시키지 않는다.

```text
원본 SHA와 quality gate source SHA 일치
repaired SHA와 quality gate repaired SHA 일치
지원되는 원본 brain record 손실 = 0
설명되지 않은 artifact/record 변환 = 0
raw_record_count == normalized_record_count
import_loss_audit_passed = true
missing_source_reference_count = 0
missing_payload_reference_count = 0
provenance closure 오류 = 0
모집단 underfill = 0
typed payload 오류 = 0
sample_weight_validation_status = passed
지원되는 record quarantine = 0
semantic 모순과 연결된 positive training eligible record = 0
격리 import 성공 = true
격리 deep audit 성공 = true
production 저장소 변경 = 0
```

`semantic_failure_count` 자체는 차단 조건이 아니다. 기존 semantic artifact의 명시적 모순과
연결된 positive record가 계속 학습 가능 상태로 남아 있을 때만 실패다. BLIND 관련 선언은
repair 단계에서 재판정하지 않는다.

unknown bundle/record type은 조용히 버리거나 억지로 known type으로 바꾸지 않는다.
원형을 보존하고 별도 검토 대상으로 남긴다.

import 후에는 아래가 맞아야 한다.

```text
imported = true
accepted = true
raw_record_count == normalized_record_count
raw_training_eligible_record_count == training_eligible_record_count
```

두뇌 갱신 후에는 아래가 맞아야 한다.

```text
warehouse verify passed = true
brain audit coverage_complete = true
brain audit deterministic_rebuild_verified = true
brain audit findings count = 0
```

`catalog --allow-catalog`는 import 이후의 로컬 smoke에는 사용할 수 있지만 production
brain 승격으로 간주하지 않는다. production은 real LLM/embedding/provider를 사용한
`llm-full`, production memory index, `doctor --production`까지 통과해야 한다.

## repair가 하는 일

repair는 연구 내용을 새로 만들지 않는다.

하는 일:

```text
record id 전역 namespace 부여
front matter / manifest / direct ingest contract 정규화
record count / hash / validation report 재계산
source/fact/inference provenance 보강
known record_type으로 변환 가능한 record 정규화
학습에 부적합한 record는 보존하되 training_eligible=false 처리
sample_weight 합계 검증이 닫히도록 정규화
```

하지 않는 일:

```text
새 종목 지식 추가
새 수혜 관계 추가
뉴스-가격 판단을 새로 창작
가격 결과를 바꿔치기
연구 내용을 임의로 풍부하게 조작
```

## training eligible의 의미

`record_count`는 보존된 전체 두뇌 record 수다.

`training_eligible_record_count`는 그중 학습 원료로 바로 써도 되는 record 수다.

예:

```text
20241203: 341 records / 210 training eligible
20241111: 458 records / 295 training eligible
```

나머지는 버린 것이 아니다. audit, context, provenance, 검증 기록으로 남는다.
다만 근거가 덜 닫혔거나 importer가 학습 타입으로 보지 않는 record는 학습 샘플에서 제외한다.

## repaired record가 두뇌에서 쓰이는 방식

Phase B import 이후 repaired `brain_delta`의 모든 record는 `memory/records/`에 보존되고
warehouse와 production vector index에 투영된다. 근거 유효성과 결과 방향은 서로 분리한다.

```text
training_eligible=true
→ 근거·provenance·label 계약이 닫힌 유효한 record라는 뜻
→ record type에 맞으면 SFT/preference/eval export 대상
→ 호재 또는 positive라는 뜻은 아님

training_eligible=false
→ training export 제외
→ positive analog와 positive claim 근거에서 제외
→ exhaustive memory에는 보존
→ negative control / near miss / boundary / audit context로만 활용 가능
```

호재·무반응·반례 방향은 `training_eligible`과 별도로 record type 및 outcome으로 계산한다.

```text
training_eligible=true + evidence_polarity=POSITIVE
→ positive_analogs 및 llm-full positive claim 근거

negative_control_case 또는 약한/음수 outcome
→ training_eligible=true여도 negative_controls로 라우팅
→ 유효한 negative calibration 학습 원료로 사용 가능

newsless_or_unexplained_case
→ newsless_or_unexplained 전용 라우팅
→ 가격 상승을 보고 원인 뉴스를 사후 창작하지 않게 하는 기억

candidate/ranking error와 근거 미충족 positive outcome
→ near_misses 또는 candidate_generation_errors로 라우팅
```

모든 record에는 `available_from`이 유지되므로 일일 분석 cutoff보다 미래인 연구는 검색·sweep
문맥에 들어오지 않는다. semantic retrieval은 현재 뉴스 event cluster마다 positive analog,
negative control, near miss, counterexample, leader selection, theme failure, candidate-generation
error, newsless/unexplained 경로를 나눠 검색한다. 검색 결과는 후보 생성의 참고 문맥이며 하드코딩된 종목·테마
판정표나 후보 차단 규칙으로 사용하지 않는다.

semantic 모순 때문에 제외한 positive record는 삭제하지 않는다. `eligibility_reason`과
`semantic_exclusion_relation_ids`를 compiler와 daily memory sweep에 전달해, 두뇌가 그 사례를
성공 패턴으로 배우지 않고 실패 경계/near miss로 기억하게 한다.

## sample weight의 의미

`sample_weight`는 매매 비중이 아니라 학습 샘플 비중이다.

같은 날짜/같은 종목/같은 사건 묶음에 record가 여러 개 있으면 전부 `1.0`으로 두면
그 종목 하루가 과대표현된다. 그래서 한 그룹의 합계가 1.0이 되게 나눈다.

예:

```text
3개 record 그룹 = 0.333333 + 0.333333 + 0.333334 = 1.0
```

이 처리는 연구 내용을 바꾸는 것이 아니라 학습용 포장 균형을 맞추는 것이다.

## repair 실패 처리

이 단계에서는 재연구하지 않는다. wrapper/manifest/count/type/sample_weight/provenance 문제가
남으면 같은 원본 구조를 읽는 범용 parser/normalizer를 보강하고 같은 파일을 다시 repair한다.
semantic 모순은 파일 전체를 막지 않고 연결된 positive record만 학습 제외한다. BLIND 연구
판정은 후공정에서 새로 만들지 않는다.

## 좋은 상태의 의미

좋은 상태는 아래처럼 말할 수 있다.

```text
repaired 통과
inspect 통과
import/accept 성공
known/supported record quarantine 0
unknown record/type은 silent drop 없이 별도 보존·검토
warehouse verify 통과
brain rebuild/audit 통과
record 손실 0
```

이 상태면 해당 연구 번들은 프로젝트의 장기 두뇌 원료로 들어간 것이다.
